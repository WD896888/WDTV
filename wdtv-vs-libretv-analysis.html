0. 结论速览

一句话：WDTV 在「播放链路深度 + 社交/账号 + 离线能力」上明显领先，LibreTV 在「内容发现 + 源治理 + 工程化 + 安全」上明显领先。两者不是新旧替代关系，而是互补：值得做的是把 LibreTV 的产品设计与治理机制移植进 WDTV 现有架构，而不是把 WDTV 迁到 Next.js。
  • 不是"LibreTV 功能更多"。WDTV 早已实现换源测速、画质探测、hover 预取详情、下一集 manifest 预取、广告分片过滤、整集离线缓存、下载器、录屏、弹幕、共看房间、账号云同步——这些 LibreTV 重构版大多没有或更浅。
  • LibreTV 真正领先的是"把复杂度收拢起来"的方式：服务端聚合搜索与逐源流式返回、跨源同名卡片聚合、数据源订阅与阶梯式健康度、片头/中段/片尾跳过标记、播放错误恢复策略、画质探测队列、统一状态组件与错误边界、37 个单测文件 + TypeScript + CI。
  • 最值得先做的三件事：① 跨源同名卡片聚合（纯前端、收益立竿见影）；② 播放错误恢复的"决策/执行分离 + 连续失败换源"（WDTV 当前错误路径散落在 6433 行 player.js 里）；③ 片头片尾跳过标记（用户感知最强，且 WDTV 的播放器基础设施完全够用）。
  • 最该修的不是功能，是安全：functions/proxy/[[path]].js 明确写着"代理层不做密码校验"，且没有 SSRF 防护，是一个可被任意第三方利用的开放代理；而 LibreTV 有 DNS 解析后校验 + 逐跳重定向重校验 + 会话签名 + 登录限流。这一项优先级高于所有体验改进。

1. 血缘、定位与规模

2. 架构与请求链路

WDTV：浏览器为中心 + 边缘函数

浏览器
 ├─ 搜索/详情 ─直连采集站─┐
 │      └失败→ /proxy/    │
 ├─ m3u8/ts ─/proxy/ → CF KV + Cache API
 ├─ 弹幕 ─/danmu/ → 弹弹play
 ├─ 账号 ─/api/ → D1
 ├─ 共看 ─WebSocket→ Durable Object
 ├─ 离线 ─Service Worker + IndexedDB + Cache Storage
 └─ 静态 ─CDN（?v= 版本化）

核心思想：能放浏览器就放浏览器，服务端只做必须同源的转发与账号。静态资源几乎零成本，视频流走边缘缓存。

LibreTV：服务端为中心 + 全栈单体

浏览器(React)
 ├─ /api/search  ← 服务端并行聚合 N 个源
 ├─ /api/detail  ← 服务端解析 CMS/详情页
 ├─ /api/proxy   ← Cookie 会话 + SSRF 校验
 ├─ /api/live/*  ← M3U/EPG/测速/流转发
 ├─ /api/quality ← 流式画质探测
 └─ 本地 IndexedDB（历史/进度/分片缓存）
      ↑ 所有用户数据不出浏览器

核心思想：把不可控的第三方请求全部收拢进服务端，浏览器只负责渲染；数据源、订阅、健康度由服务端统一治理。

2.1 搜索链路：最大差异

WDTV 的优势别丢：直连优先 + 失败回退代理，比 LibreTV"所有请求都过服务端"少一跳，在国内网络环境下首屏更快，也省 Functions 配额；linkAbortSignal 把"新搜索 abort 旧请求"和请求自身超时合并，是写得很干净的一段。LibreTV 的劣势是代理成为单点且所有源站流量都吃服务器带宽。
但 WDTV 的代价：浏览器直连会向采集站暴露用户真实 IP、绕过同源策略依赖对方 CORS、无法做服务端缓存；且 /proxy/ 是无鉴权、无 SSRF 校验的开放代理。

2.2 播放链路

两边都用 ArtPlayer + hls.js，且都实现了广告分片过滤、自动连播、进度记忆、倍速/快捷键。差异在"精细化程度"和"策略组织"：

  • WDTV 更激进也更深：js/ad-filter.js 是 694 行的多机制融合引擎（SCTE35/DATERANGE 标记层 → DISCONTINUITY 区间评分层 → 广告域名黑名单层 → 运行时 seek 兜底），带 40% 删除预算、剩余分片下限、BYTERANGE/合法区间一票否决、规则版本签名注入（#WDTV-ADF: 变更即缓存失效），并且是唯一有单元测试的模块。js/video-cache.js 2,134 行实现 IndexedDB 整集缓存 + hls loader 读写穿透 + 12 并发后台下载 + 缓冲不足自动让路 + 3GB/3天/3集 LRU + 孤儿对账；player.js 还实现了"始终锁定最高画质"（取消 ABR 降档）、档位探测的 tierProbeToken 竞态令牌、首分片预取、下一集 manifest 预取、换源测速（Range 流式实测码率 + 吞吐）、录屏/截图（安卓 captureStream 直捕 + VP8 软编码取舍）。
  • LibreTV 更克制也更有章法：把策略从播放器里拆成可单测的纯函数模块——playback-recovery.ts 只产出 RecoveryDecision 不碰 hls 实例，区分硬失败（直接换源）与网络抖动（退避重试），FRAG_LOADED 即把连续失败计数归零、动作后 3s 静默窗防噪声；quality-probe-queue.ts 是全局单例队列（同 key 共享 Promise、50ms 合批、最多 2 个在飞/每批 8 条、看门狗防槽位占死、onStart 才显示"探测中"）；video-prefetcher.ts 刻意不在循环体里读播放状态，所以暂停/切后台仍继续缓存；live-cache.ts 因通用缓存超限时整体 clear() 会连带清掉热点数据，专门做了独立的按字节 + 条目双上限 TTL 缓存。
这一组的判定：WDTV 的"能力"更强，LibreTV 的"可维护性"更好。WDTV 的这些逻辑全塞在 player.js 里靠注释和全局令牌维护，改一处容易踩另一处；LibreTV 每个策略都能单独跑测试。借鉴时应当学它的拆分方式，而不是替换 WDTV 已有的能力。

还有四处实现细节值得单独记下，都是低成本可移植的：

  • 换集不重建播放器实例。player-shell.tsx 的 loadSource 在切集/换源时只 hls.destroy() → 复用同一个 <video> → attachMedia → 等 loadedmetadata，ArtPlayer 实例、主题、倍速、音量、字幕、控制条、跳过标记全部跨集保留；倍速由 sessionStorage 记忆并只从 watch 页写入，避免跨页串扰。WDTV 走的是相反路线："整条 URL 换源重建播放器 + 进度无缝恢复"（player.js 第 800 行注释），好处是状态干净，代价是每次换集都要重挂弹幕插件、缓存 loader、下载面板等一整套东西。
  • 播放层也有直连→代理回退。hls-loader.ts 的 buildCandidateUrls 按「direct→proxy→imgproxy」给每个分片生成候选，switchToProxyOnRepeatedFailures() 连续直连失败 2 次后把该集剩余分片全部改走代理，成功后用同一个开关切回直连。这与 WDTV js/api.js 的 fetchWithFallback 思路一致，只是 WDTV 作用在搜索/详情请求，LibreTV 作用在播放分片。
  • 缓存命中不能让 ABR 误判带宽。video-cache.ts 把预取时记录的真实 costMs 存进 segmentMeta，命中本地分片时合成进 hls.js 的 stats，否则"本地秒回"会被 ABR 当成带宽暴涨而盲目升档再抖动。WDTV 因取消 ABR 锁最高档，恰好没有这个问题——这是架构取舍带来的意外收益。
  • URL 驱动可分享状态。搜索词写进 /?s=、播放状态写进 /watch?source=&id=&index=&title=、直播写进 /live?url= 且故意不含 EPG（避免刷新必重拉大文件），换集用 replaceState 不污染历史；popstate 单独处理浏览器前进后退。进度条用原生 input[type=range] 而非 ArtPlayer 自带控件，因为后者暂停时隐藏、无法在暂停态 seek。

4.1 服务端聚合搜索 + NDJSON 逐源返回

src/app/api/search/route.ts：每源先取第一页读 pagecount，再并行抓后续页（上限 5）；每源一个 AbortController + 定时器组成总死线（默认 10s），与 Promise.race([runPromise, deadline]) 竞速，到点 abort 在途请求并把该源标记为 timedOut；?stream=1 用 ReadableStream 以 NDJSON 逐源推送，X-Accel-Buffering: no 防反代缓冲，客户端 React Query 管理状态、已就绪源数实时显示。

为什么好：一个坏源不再拖垮整次搜索；失败源在结果区顶部非阻塞提示；服务端可缓存；浏览器不暴露 IP。借鉴：WDTV 不建议整体改成服务端聚合（会丢直连速度优势、增加 Functions 配额），但可以借鉴单源总死线和逐源结算的失败归因——目前 fetchWithFallback 只有单请求预算，一个源的多页补抓没有整体死线；另外可把"已就绪 N/M 个源"和"失败源提示"做成非阻塞条，替代现在的整块 loading。

4.2 跨源同名卡片聚合

src/components/video-card.tsx 的 aggregateResults()：按 normalizeTitle 后的名称分桶，桶内年份不一致时按年份再拆（同名翻拍），无年份条目并入年份桶；卡片显示「N 源」徽章，点击展开源列表，展开时按画质探测结果降序排列并标出最佳源；单源卡片则进视口 500ms 后才交给全局队列探测。

为什么好：十几个源搜同一部片时结果页不再被重复海报淹没，且把"选哪个源"这个决策从播放页前移到搜索页，配合画质徽章一次做对。WDTV 现状：js/app.js 只有"同名筛选下拉"（统计出现 ≥2 次的片名让用户过滤），卡片仍是扁平的；用户要进详情/换源弹窗才知道有几个源。借鉴成本最低、收益最高：结果数据已在 app.js 的 currentSearchResults 里，只需在渲染前加一个分桶函数 + 卡片展开面板，复用现有 .wdtv-search-grid 样式即可。

4.3 源健康度阶梯停用 + 订阅体系

src/lib/store.ts：连续失败的源按「30 分钟 → 24 小时 → 长期停用」逐级加重，成功一次降一级，长期停用只能手动恢复；subscription-sync.ts 用订阅 URL 前缀整体替换该订阅名下的源、保留用户勾选状态、同步失败不调用即无副作用（旧数据自动保留）；tvbox-parser.ts 兼容 TVBOX 配置里的 // 注释、尾随逗号、字符串内未转义换行，并如实报告"跳过 96 个不可用条目（Spider 引擎 92、XML 接口 4）"。

更细的工程细节值得单独记下：src/app/api/source-list/route.ts 的 parseAndValidate() 用内容嗅探而非让用户选格式——按 sources/liveSources → sites/lives（TVBOX）→ 裸数组全带 baseUrl（接口目录）依次试探，且 TVBOX 与 LibreTV-SourceList 同为对象时靠 sites/api.php/provide/vod 三重特征+阈值判定（≥1 个 API 特征，且 sites.length > sources.length 或 liveSources.length > sites.length），防误判；JSONC 清洗用状态机跳过字符串内 //、去尾逗号、把字符串内裸换行转义为 \\n；/api/publish 用 AbortSignal.timeout(8000) 串行试 paste.rs → 0x0.st。自动刷新只在 providers.tsx 挂载时检查一次（并发 2、单次最多 5 个、页面不可见或离线跳过、不阻塞首屏），连续失败 3 次自动暂停订阅。

为什么好：采集站经常批量失效，用户不需要手动逐个取消勾选；订阅让源配置可分享、可远程更新。WDTV 现状：js/api.js 的健康度只有 10 分钟 TTL 的"延后发起/跳过直连"，没有停用；源列表硬编码在 js/config.js 的 API_SITES 里，改源要改代码。借鉴：把健康度升级为阶梯停用（约 80 行），并增加"远程源列表 URL + 每日静默刷新"（可与现有 cloud-sync 结合，把源配置也纳入同步包）。

4.4 片头 / 中段 / 片尾跳过标记

最见产品功力的一处。src/lib/skip-marks.ts 定义三类片段、颜色、最小 3s 长度、5s 最小间隔、片尾 2s 保护、10s 连续步进上限，以及 skipMarkKey(title, fallback) 让同剧各集与同名资源共用标记；player-shell.tsx 实现自动跳过（片头/中段跳到片段末尾，片尾直接结束本集并交给自动连播）、12 秒撤销窗口（撤销后把该片段从"已处理"移除，否则回到片段内会被 timeupdate 立刻再跳走形成死循环）、进度条着色（data-skip-segment 元素在 durationchange/fullscreen/resize 时重绘）；skip-mark-panel.tsx 用 modal=false 的非模态抽屉，不遮画面、不锁 body、不抢焦点，可以一边看一边标，还能微调边界、试跳起终点（记录/试跳前先暂停）。

借鉴：WDTV 的 ArtPlayer 实例、进度条 DOM、设置面板都已就绪，缺的只是"标记数据 + 规则 + 提示 UI"。建议先做最小集：本地按剧保存 opening/ending 两个区间 → timeupdate 命中自动 seek → 提示条带撤销 → 设置里总开关；再做进度条着色与非模态面板。注意 WDTV 已有"广告自动跳过"开关，两者语义要在设置里明确区分，避免用户混淆。

4.5 播放错误恢复：决策与执行分离

src/lib/playback-recovery.ts 的注释直接点明了旧实现的问题："遇致命错误就无条件 hls.startLoad()，errorCount 只增不减，源站挂掉时形成无限重试风暴，且永远不会换源"。它的做法是纯函数产出决策：硬失败（manifestParsingError / incompatibleCodecs / levelEmpty）直接换源，网络类失败退避重试；FRAG_LOADED（含本地缓存命中）即视为链路恢复、计数归零；动作后 3s 静默窗内成功不清零，防重试瞬间的噪声。

但要公平：WDTV 的错误恢复能力本身不弱，只是写法不同。player.js 的 Hls.Events.ERROR（:2075）已实现坏缓存自愈（FRAG_PARSING_ERROR/BUFFER_APPEND* → VideoCache.invalidateFragment() 删缓存强制走网络）、bufferAppendError 累计 ≥3 次 recoverMediaError()、致命 NETWORK_ERROR→startLoad() / MEDIA_ERROR→recoverMediaError()、其余累计 >3 次才弹错，另有 hls.js 1.6 ENDED 态 seek 卡死的兜底；video-cache.js 还有 FAKE_CACHED_SPEED_BPS=3Mbps 合成速率防 ABR 误判，与 LibreTV 的 costMs 是同一个洞见。差距只在结构：这些分支与缓存、弹幕、录屏状态交织在 6,433 行里，无法单测、阈值散落、改一处容易踩另一处。所以借鉴的是「抽成纯决策模块 + 补测」，不是「补功能」。

借鉴：把 player.js 里散落的 hls 错误处理抽成独立 js/playback-recovery.js（IIFE，纯函数，可仿照 ad-filter.js 那样写 .test.mjs），播放器只执行决策。这是降低 6433 行巨石维护风险最划算的一刀。

4.6 画质探测队列

quality-probe-queue.ts：同 key 共享 Promise、50ms 合批、最多 2 个在飞 / 每批 8 条、单批失败不影响队列、服务端提前关流时按"已取消"收尾、看门狗防 2 个并发槽被永久占死、onStart 在批次真正发出时才回调（排队期间不谎报"探测中"）。配合 use-in-view.ts（进视口后再等 500ms，快速滚过不触发，一旦置位永久保持）。

借鉴：WDTV 的 app.js 已有「联网探测时长」功能（probeItemDuration，仅探测当前页、会话内缓存），若把跨源同名聚合 + 画质徽章一起做，必须同时引入这类队列，否则一屏十几张卡会瞬间打满请求，重蹈 WDTV 曾经"搜索时 hover 预取挤占连接池"的覆辙（源码里已有这个教训的注释）。

4.11 安全模型

src/lib/ssrf.ts：协议白名单 + 字面量 IP 黑名单 + IPv4-mapped IPv6 归一化（::ffff:c0a8:164 也要能识别）+ dns.lookup(all:true) 解析后校验，任一解析结果落私网即拒绝；fetch-utils.ts 的 fetchWithSafeRedirects 用 redirect:'manual' 逐跳重新校验（注释："预检之后 fetch 自动跟随的 3xx 可把请求带进内网/元数据地址，绕过对首跳的校验"），最多 5 跳，并返回 finalUrl 供 manifest 相对地址解析使用；auth.ts 的签名 Cookie + IP 限流；代理路由要求会话，未登录仅放行图片类目标。

WDTV 对照（最高优先级风险）：functions/proxy/[[path]].js 第 15 行注释明确"前端不携带 auth 参数……代理层不做密码校验"，getTargetUrlFromPath() 只校验 ^https?://，没有 host 白名单 / 私网 IP 判定 / 逐跳重定向校验，fetch(targetUrl,{redirect:'follow'}) 自动跟随 302；响应还是 Access-Control-Allow-Origin: *。而 /proxy/ 并不只代理视频——js/api.js、js/douban.js、js/app.js、js/connection-test.js 都把 CMS 搜索/详情、豆瓣图片、连接测试塞进同一个代理，等于一个无鉴权、无目标白名单的通用开放代理。

更讽刺的是本地比生产安全：server.mjs 的 isValidUrl() 有 BLOCKED_HOSTS + BLOCKED_IP_PREFIXES（172.16/12 逐段列出避免误伤公网）+ 协议白名单，但 .env.example 里的 BLOCKED_HOSTS/BLOCKED_IP_PREFIXES/FILTERED_HEADERS 这些变量云端 Functions 一行都不读（云端过滤列表是硬编码的），容易让部署者误以为生产也有防护。这一项应优先于任何体验改进：至少加协议/私网 IP 黑名单 + 同源 Referer 校验 + 目标域名白名单（限定采集站与已知图床），手动跟随重定向并逐跳校验；注意 Workers 无 node:dns，LibreTV 的 DNS 解析后校验无法照搬。

但别把 LibreTV 的安全模型神化，逐文件核对后发现几处同样明显的缺口：① 仓库里没有 middleware.ts，鉴权靠每个 Route Handler 手动调 guardRequest(req)（内部 sessionFromCookieHeader → verifySession），新增路由极易漏挂；/api/auth 和 /api/status 才是有意豁免。② 只校验 Cookie，没有入站 Origin / CSRF token 校验——代码里的 Referer 是伪装成上游站点的出站请求头，勿混淆；之所以风险可控，靠的是 Cookie SameSite=Lax + application/json 触发预检，属于"恰好安全"而非显式设计。③ 登录态的 isBlockedByDNS 解析失败时返回 false 放行（注释写明"解析失败不阻断，交给后续请求处理"），而后续 fetchUpstream 仅在 safeRedirects 开启时才重查 DNS，理论上存在 DNS rebinding 窗口。④ 限流、搜索缓存、画质探测结果、直播缓存全是进程内 Map，多实例部署各自为政，README 里也提示多实例要显式设置 PROXY_SECRET。⑤ 无服务端数据库、无账号体系，db.ts 只有 6 张浏览器表；无实时推送式跨标签页同步（全仓 BroadcastChannel / storage 事件零命中），但有懒重读缓解：download-manager.tsx 靠抽屉打开时重读 loadDownloadSettings()、use-quality-probe.ts 的 sharedQueue 只是当前标签页的模块级单例；两个标签页并发写入仍是后写覆盖、无版本号仲裁。Zustand persist 靠 800ms 节流 + skipHydration 手动 rehydrate，仅在 visibilitychange(hidden) / beforeunload flush，仍可能丢最后几次写入。⑥ 服务端 60s 搜索缓存只在同一进程有效，且代理默认 s-maxage=300 只对公开 CDN 生效；⑦ ssrf.ts 是黑名单式防护（拒绝内网）而非出站域名白名单，登录用户仍可让它代理任意公网 URL，实质仍是"有额度约束的开放代理"；checkUpstreamAllowed 与 checkLiveUrlAllowed 还是"两把尺子"（后者可由 LIVE_ALLOW_PRIVATE=1 放行内网 IPTV）。
所以准确结论是程度差，不是有无差：WDTV 生产端是「零校验 + 完全匿名」的开放代理，LibreTV 是「有校验 + 需登录 + 有额度约束」的开放代理。WDTV 连登录这层都没有，仍是全篇最严重的风险点，定位不变。

5. WDTV 更优、不该被"重构掉"的部分

迁移到 Next.js 会真正失去、且重构版零实现的是这六项（已对 src 全量检索确认）：弹幕（弹弹play 匹配 + 三源降级）、Durable Object 共看房间、D1 账号云同步（按 key 类型合并的冲突解决）、Service Worker 页面级离线、截图 / 录屏、观影空间 / 我的影院。此外还会引入常驻 Node 进程成本、丢掉 Cloudflare 边缘缓存与 _routes.json 的"静态直出不消耗 Functions 配额"设计。

但不要夸大差距：广告过滤、视频缓存、下载器三项重构版都有对等实现——m3u8.ts 四级启发式经 hls-loader.ts 的 onSuccess 接入（设置里「广告切片过滤」开关）、video-cache.ts + video-prefetcher.ts（Cache Storage + Dexie 两轮 LRU，默认单集 800MB / 全局 2GB）、download-manager.tsx + m3u8-downloader.ts（并发 8、WebCrypto AES-128、mux.js 流式转封装、断点续传）+ download-saver.ts（FS Access 磁盘直写）。差别是策略与深度：WDTV 更细、默认更激进（3GB / 自动缓存默认开），重构版更保守、且无 SW 所以页面离线仍不可用。

另外 WDTV 有些实现细节明显更贴合真实网络环境，例如 video-cache.js 的 FRAG_DIRECT_TTFB_MS=6000 注释记录了"蜂窝网冷启动普遍 >3.5s，旧版按总时长 3.5s 掐会误杀可用直连，把整个会话锁进跨境代理导致卡顿"；player.js 的"始终锁定最高画质、取消 ABR 自动降档"；ad-filter.js 的规则签名缓存失效。这些都是踩坑换来的。LibreTV 的广告过滤走的是另一条保守启发式路线（宁可漏删也不误删，见 3. 功能矩阵），画质上保留 hls.js 原生 ABR 而非锁最高档，两者都是"稳"优先于"狠"的取舍，不能简单判为落后。

还有一条架构优势：WDTV 的 _routes.json 只让 /proxy/* /api/* /danmu/* 走 Function，其余纯静态直出；_headers 对 /libs/ 设 1 年 immutable；代理内部又把 m3u8（120s）与 ts 分片（24h）缓存分离，并用 caches.default 显式边缘缓存（注释记录了"Function 响应即便带 Cache-Control 也恒为 CF-Cache-Status: DYNAMIC"这个实测结论）。这套边缘缓存精细度是 LibreTV 的内存 Map 缓存比不了的。

还有一处容易被忽略的工程亮点：js/downloader.js 用 Web Locks API（navigator.locks.request 的 ifAvailable/steal）+ localStorage 心跳（检测持锁页签被冻结）+ PUMP_EPOCH_KEY 代数让位，实现了跨页签下载调度；另有 wakeLock 防手机锁屏冻结、IndexedDB 800ms 节流落库支持刷新续传、EXT-X-DISCONTINUITY 造成的 PTS 重置逐分片重排时间线。反倒是重构版的下载管理器只管当前标签页，跨页签靠"抽屉打开时重读设置"的懒同步——这一项 WDTV 做得更完整，也说明"跨标签页状态"在两边都是局部解决、不是系统能力。

6.1 别把"工程化领先"误读成"全面领先"

逐文件核对后，LibreTV 重构版自身也有明确的代价，这对判断"该抄什么、不该抄什么"很关键：

  • 几乎全是 CSR。首页、watch、live、about 都标 'use client'，所有 API 路由显式 runtime='nodejs'。SSR 阶段输出的只是一层壳与 Spinner：布局会先渲染 <div class="min-h-screen bg-base">，再靠 Providers 的 useEffect 把 auth 状态改成已验证才渲染 Header；QueryClientProvider 还要 useState 懒创建。也就是说首屏内容、搜索、推荐全靠客户端 JS 拉取，SEO 与低端机首屏都不占优。WDTV 的页面结构随 HTML 直出、数据源由浏览器直连，不必等服务端聚合，Functions 全挂时仍能搜索，这一项确实更皮实。但别把 WDTV 当成"轻量静态页"：index.html 同步加载 407KB 的浏览器内 Tailwind JIT（libs/tailwindcss.min.js）、约 500 行内联 CSS 与约 700 行内联 canvas 水波/雨滴特效 JS，18 个业务脚本全是同步 <script src>（无 defer / module），首屏阻塞并不小；而 player.html 又全用 defer（唯 cloud-sync.js 例外），两页加载策略还不一致。准确结论是"无服务端数据依赖"，不是"无 JS 开销"。
  • 依赖体积大。Next/React 19/React DOM + hls.js + artplayer + mpegts.js + mux.js + Dexie + Zustand + TanStack Query/Virtual + Tailwind；且因上游图片地址运行时不可枚举，images.unoptimized:true 关闭了图片优化，仍用原生 <img>。WDTV 零构建、依赖全部本地化在 libs/，没有 CDN 运行时依赖。
  • 测试偏科。37 个测试文件几乎全是纯逻辑单测（ssrf、cms-parser、m3u8、store、quality-probe、tvbox-parser…），没有 React 组件测试、没有 E2E、没有 jsdom；恰恰最复杂的 source-manager.tsx（1,357 行）与 player-shell.tsx（1,067 行）没有测试覆盖。PlayerShell 为"切集不重建播放器"引入 propsRef 让闭包读最新 props，作为补偿也把数据流隐式化了。
  • PWA 是半套。有 manifest + 全尺寸 icons + display:standalone，但没有 Service Worker，离线连页面都打不开；视频片段缓存只解决播放不解决页面。WDTV 的 SW + 整集缓存才是完整离线方案（见第 5 节）。
  • 强服务端绑定。所有第三方请求（含搜索、详情、画质探测、订阅解析）必须经同源 Next 服务，部署者必须常驻 Node；离开服务端整个应用不可用。WDTV 的"浏览器直连 + 边缘代理兜底"在可用性上更皮实，代价是安全与隐私（见 4.11）。
  • 本地数据也有配额风险。Dexie 6 表 + Cache Storage 默认 2GB 上限、会请求持久化存储（可能被浏览器拒绝）；WDTV 是 3GB 软上限 + 3 集/3 天 LRU。两者都需要配额兜底，不是某一方独有问题。

6.2 四个更底层的架构对照（最容易被表面结论掩盖）

  1. 冷启动 / 常驻，两边都有成本，形态不同。LibreTV 是常驻 Node 进程，不存在函数冷启动；真正的启动成本在「每次进程重启后内存缓存全空 + Next 首次编译/加载」，以及平台缩容到零后的首请求延迟（其 Docker/standalone 部署模型下不必然发生）。WDTV 的 Pages Functions / D1 / KV 是按请求拉起的无状态边缘运行时，而 sync-worker 的 Durable Object 走的是 WebSocket Hibernation API（state.acceptWebSocket(server) + webSocketMessage / webSocketClose 事件唤醒），webSocketClose 后立即 delete this.room，无连接时不占常驻内存、不计费，靠 SQLite 事务表续命。准确说法是"WDTV 用 DO 的 hibernation 换掉了长连接常驻成本，LibreTV 根本不提供实时协同所以没有这项成本"，而不是笼统说"Serverless 一定比常驻便宜"。
  2. 状态跨实例共享，两边都不彻底，只是断在不同边界。WDTV 的边界是运行时：生产端所有共享态外置到 KV（m3u8 缓存）/ D1（账号与快照）/ DO（房间），Functions 无状态；但本地 server.mjs 把会话、房间、密码、日志全放在进程内 Map，重启即丢、多实例无共享——生产无状态、开发有状态，这正是"同形 API"最容易掩盖的漂移。LibreTV 的边界是边缘渲染层 / 应用状态层：SSR 元数据与客户端 Zustand（IndexedDB + localStorage）刻意分离，靠 rehydrate 合流；以及集群边界：搜索缓存、鉴权限流、画质探测队列订阅者、直播缓存全是进程内 Map，多副本部署各自为政，README 才提示多实例要显式设 PROXY_SECRET。
    一句话：WDTV 把共享态推给了云基础设施，LibreTV 把共享态留在了进程里。两边都没有做"多实例完全一致"，只是 WDTV 在生产环境做对了。
  3. 账号模型差在三项能力，不只是"有没有注册"。① 全局鉴权层：WDTV 在 functions/api/_lib.mjs 显式做 verifyAuth() 并逐路由调用，LibreTV 没有 middleware.ts，靠每个 Route Handler 手写 guardRequest(req)，新增路由漏挂的风险更高；② 会话可吊销性：WDTV 是 stateless JWT，没有黑名单/会话表，签发后到过期前无法单端吊销，只能靠 logout 删本地 token（改密码强制下线靠 tokenVersion+1 间接实现）；LibreTV 的签名 Cookie 同样无服务端吊销列表，两边都靠短 TTL（7 天 / 4 小时）兜底，这一项都不完整；③ 多端实时同步：只有 WDTV 具备（D1 云端快照 + revision CAS 乐观锁 + DO 房间 WebSocket），LibreTV 的观看历史/进度/收藏只在本机 IndexedDB，换设备即丢。所以 WDTV 在账号能力上是更完整的那一方，别因为"LibreTV 更现代"就误判。
  4. 构建与版本口径。LibreTV 的 output:'standalone' 是条件开启（DOCKER_BUILD === '1' 才生效，因为本地 next start 不支持 standalone），版本号由 next.config.ts 构建期读 package.json 注入 APP_VERSION、/api/status 可核对——这是 WDTV 最该抄的一条（见 4.10）。测试口径也应对齐：LibreTV vitest.config.ts 环境为 node、仅收 src/**/*.test.ts，37 个文件中 5 个是 route 级、32 个是 lib 级，零组件测试、零 E2E、零浏览器环境；WDTV 只有 test/ad-filter.test.mjs，且 package.json 连 test 脚本都没有，靠手工 node test/xxx.mjs 运行。

8. 落地约束（本项目特有，务必遵守）

  • Service Worker 缓存：HTML 走 Network-First，/css/ /js/ /libs/ /image/ 走 Stale-While-Revalidate，同一个 ?v=N 网址会持续返回旧文件。凡修改 CSS/JS，必须同步：① 升 index.html（及 deploy-dist/index.html 镜像）里对应资源的 ?v=；② 在 service-worker.js（及镜像）顶部 changelog 加 vN（日期）：改动说明… 升 ?v=N。否则线上永远拿不到新代码。另注意当前 service-worker.js 顶部 changelog 已记到 v62，而 CACHE_VERSION = 'wdtv-sw-v55'（install/activate 用它 purge 旧缓存）——两者已经漂移，意味着 v56~v62 的改动没有触发缓存名变更，只能靠 ?v= 换 URL 生效；建议下次发版把 CACHE_VERSION 一并递增或在构建脚本里自动关联。手工 ?v= 也已出现漂移实例：video-cache.js 在 index.html 是 ?v=95、在 player.html 是 ?v=96；此外 VC_VERSION=94、RULES_VERSION=1 又各有独立版本号。
  • deploy-dist 镜像：与根目录同构，改动需两边同步；发布前自检 find deploy-dist -type f | wc -l 应为 48（曾出现只剩 12 个根文件导致线上静态资源 404）。
  • _routes.json：当前 include 为 /proxy/* /api/* /danmu/*；新增 /api/source-list 等路由已被覆盖，但若新增其他路径前缀必须同步加白名单，否则纯静态直出会 404。
  • Functions 10ms CPU：弹幕层已有"不解析 body"的规避注释。复杂的 TVBOX/XMLTV 解析、批量探测不要放进 Pages Function，放浏览器端或独立 Worker。
  • AUTH_SECRET：同时决定 JWT 签名与密码哈希，部署后永远不要改，否则全部账号立即无法登录；且未设置时 functions/api/_lib.mjs 会回退到硬编码公开默认值（与本地开发一致），线上必须先执行 npx wrangler pages secret put AUTH_SECRET，可用 /api/config 的 authSecretSet 字段自检。Durable Object Worker 必须设成同值。

10. 建议路线图

  1. 第一步（安全 + 零风险收益）：代理层 SSRF/Referer/白名单加固；跨源同名卡片聚合；统一状态组件与图片降级链。三者都不碰播放内核。
  2. 第二步（播放器体验）：片头片尾跳过标记最小集 + 播放错误恢复策略抽离并补测；同时把 player.js 的错误处理路径收敛到新模块。
  3. 第三步（源治理）：健康度阶梯停用、失败源提示、远程源订阅/源配置云同步、画质探测队列与徽章。

  5. 第五步（品类决策）：首页推荐增源、直播 IPTV 是否引入——这两项应先确认产品方向，再评估 CF 边缘限制。
